# 예시: "부동산 대시보드 만들어줘"를 제대로 된 프롬프트로

> 실제로 이 프롬프트 한 번으로 **10개 차트 대시보드가 한 번에 완성**된 실증 사례 (2026-07-09).
> 결과물: `~/Desktop/Harry Projects/부동산-대시보드/index.html` — 더블클릭이면 실행.
> 포인트는 **success_criteria를 검증 가능한 문장으로 쓰고, verify로 자기검증을 강제**한 것.
>
> **한 달 뒤 후속 기록 추가(2026-08-07):** 같은 프로젝트가 차트 16·섹션 13·테스트 139개로 자랐다.
> 그 과정에서 **처음 만들 때의 프롬프트로는 못 고친다**는 걸 확인했다 —
> [§ 한 달 뒤: 같은 프로젝트, 다른 프롬프트](#grown-up)가 이 페이지의 두 번째 절반이다.

---

## ❌ 일반론 (이렇게 주면 안 나온다)

```
부동산 시세 대시보드 만들어줘
```

→ 어떤 지표? 데이터는 어디서? 유료 API 써도 되나? 파일 몇 개? 실패하면?
전부 추측 → 키가 필요한 코드 + 절반쯤 도는 결과물.

## ✅ 채운 버전 (작업지시 템플릿 기반 · 실사용 원문)

```xml
<role>
너는 부동산 데이터 시각화 프로젝트를 여러 번 구축한 시니어 프롬프트 엔지니어이자
프론트엔드 아키텍트다.
</role>

<context>
부동산 매매 및 시장 동향을 빠르게 파악하기 위한 대시보드를 만든다.
상용 서비스가 아니라 개인이 로컬에서 실행하는 MVP이다.
목표는 복잡한 기능이 아니라 여러 공개 데이터를 하나의 화면에서 쉽게 확인하는 것이다.
</context>

<task>
"대한민국 부동산 시장 뷰어" MVP를 설계하고 구현한다.
확인 가능해야 하는 정보: ① 매매가격지수 ② 전세가격지수 ③ 월별 거래량
④ 거래금액 ⑤ 지역별 평균 매매가 ⑥ 지역별 평균 전세가 ⑦ 미분양
⑧ 공급(인허가·착공·분양·준공) ⑨ 기준금리×가격 비교 ⑩ 인구·세대수
⑪ 지역별 순유입/유출 ⑫ 주요 지표 요약 카드 ⑬ 마지막 업데이트 표시
⑭ 기간(1년/3년/5년/전체) 전환
</task>

<requirements>
1. GitHub 조사로 적합한 오픈소스 라이브러리·구현 사례 확인 후 진행
2. 무료 공개 API 우선, 호출 실패 시 자동으로 로컬 mock 데이터 사용
3. 스택: 단일 HTML + ES Module + 순수 JS + CSS
4. 빌드 도구(npm/webpack/vite) 금지
5. Chart.js 또는 ECharts 중 MVP에 적합한 것 선택
6. 데이터는 정부 공개 데이터(KOSIS·공공데이터포털·한국부동산원) 우선
7. 파일 수 3개 이하
</requirements>

<non_goals>
로그인 / DB / 백엔드 / WebSocket / 심볼선택 UI / 지도 / 그리기 도구 /
사용자 저장 / AI 분석 / 모바일 최적화
</non_goals>

<constraints>
유료 API 금지 · 오버엔지니어링 금지 · 파일 3개 이하 ·
실행은 index.html만 열면 가능해야 한다.
</constraints>

<success_criteria>
1. index.html 하나만 열어도 정상 실행
2. 핵심 차트 5개 이상 표시
3. 데이터 호출 실패 → mock 자동 전환으로 전 차트 계속 동작
4. 기간 전환(1/3/5년/전체) 동작
5. 데이터 출처·업데이트 시간 화면 표시
6. 전체 3개 이하 파일
7. 데이터 소스 교체가 쉽도록 fetch 함수 분리
</success_criteria>

<verify>
종료 전 Success Criteria 1~3을 스스로 검증해 결과를 항목별로 보고한 후
"MVP 구현 완료"를 선언한다.
</verify>
```

## 실제로 얻은 것 (한 번의 프롬프트로)

- 차트 10종 + 요약 카드 6개 + 기간 필터 + 표 뷰 + 다크모드 — **단일 index.html**
- 스스로 브라우저를 열어 스크린샷 검증 → 겹침·잘림 3건을 **자기 수정 후** 완료 선언
- `verify` 블록 덕분에 "완료" 선언 전 3개 기준의 증거를 제시함

## 왜 각 블록이 먹혔나

| 블록 | 없었으면 생겼을 일 |
|---|---|
| `constraints` "index.html만 열면 실행" | Chrome이 file://에서 외부 ES 모듈을 차단하는 걸 모른 채 3파일 구조 → 더블클릭하면 백지 |
| `requirements 2` (mock 자동 전환) | 정부 API는 전부 인증키 필수 + CORS 미지원 → 키 없으면 빈 화면 |
| `non_goals` 명시 | 지도·로그인까지 붙인 오버엔지니어링 |
| `success_criteria` 검증 가능 문장 | "대충 이쁘게" 수준의 완료 선언 |
| `verify` 자기검증 강제 | 겹친 범례·잘린 라벨을 그대로 두고 납품 |

> **교훈:** 제약("더블클릭 실행")이 아키텍처(단일 파일 + 인라인 모듈)를 결정했다.
> 스택 나열보다 **실행 방식·실패 시나리오**를 적는 게 구조를 바꾼다.

## 한 달 뒤: 같은 프로젝트, 다른 프롬프트 {#grown-up}

MVP가 살아남으면 요청의 성격이 바뀐다. 이 대시보드는 한 달 만에 이렇게 자랐다.

| | 2026-07-09 (MVP) | 2026-08-07 |
|---|---|---|
| 화면 | 차트 10 · 섹션 1 | 차트 16 · 섹션 13 (매수판단·내집마련·규제확인·월세수익·경매…) |
| 파일 | 3개 이하 | `index.html` + 브라우저 JS 12 + 수집 스크립트 1 |
| 검증 | 눈으로 스크린샷 | 자동 테스트 **139개** + 브라우저 콘솔 0 + 독립 재구현 대조 |
| 성격 | 시장을 **보는** 뷰어 | 사야 하나·빌려줘도 되나를 **판단하는** 도구 |

그런데 위의 MVP 프롬프트를 그대로 다시 주면 실패한다. 이유는 하나다 —
**MVP 프롬프트는 "무엇을 만들지"를 채우고, 유지보수 프롬프트는 "무엇을 믿지 말지"를 채운다.**

### 블록별로 무엇이 바뀌나

| 블록 | MVP에서 | 성숙한 프로젝트에서 |
|---|---|---|
| `context` | 왜 필요한지 | **이미 있는 것** — "새로 짓지 말고 기존 구조에 얹어라" |
| `requirements` | 스택·라이브러리 지정 | **어느 파일에 넣을지** (계산=순수함수 / 그리기=패널 / 썩는 상수=상수파일) |
| `constraints` | 오버엔지니어링 금지 | **지난번에 틀렸던 것들** (아래 표) |
| `success_criteria` | "차트 5개 이상 표시" | "기존 출력이 바뀌면 그건 회귀다" — **변하지 않아야 할 것**을 적는다 |
| `verify` | 스스로 확인하고 보고 | 테스트 전량 + 콘솔 0 + **증거를 붙여서** 보고 |

### 사건 → 제약: 프롬프트에 승격된 실패들

각 줄은 이 프로젝트에서 **실제로 한 번 틀렸던 것**이고, 그래서 다음 프롬프트의 `constraints`가 됐다.
도메인은 부동산이지만 오른쪽 열은 어디에나 옮겨 붙는다.

| 실제 사고 | 승격된 제약 |
|---|---|
| 데이터 수집이 조용히 실패해 **mock이 실측인 척** 화면에 표시됨 | 데이터가 없으면 지어내지 말고 그 카드를 **숨겨라** |
| 기준일 오타 → `NaN` 비교가 전부 false → **감시기가 "전부 정상"이라 보고** | 판정 불가는 "정상"이 아니라 **"실패"로 승격**하라 |
| 반올림된 면적값을 키로 써서 **20개 항목이 1억 이상 과대평가** | 파생값보다 **실측 표본**을 쓰고, 표본 수를 화면에 적어라 |
| 세금 계단(2,000만원) 때문에 함수가 **비단조** → 이분법이 틀린 답을 반환 | **단조성을 가정하지 마라.** 불연속점을 먼저 찾아 구간을 쪼개라 |
| 서로 다른 제도(규제지역·토지거래허가)를 한 플래그로 합침 | 지금 값이 같다고 **같은 개념으로 합치지 마라** (한시 지정은 만료된다) |
| 외부 RSS 제목을 이스케이프 없이 `innerHTML` | 외부 문자열은 전부 이스케이프, **링크는 스킴 화이트리스트** (이스케이프만으론 `javascript:`를 못 막는다) |
| 브라우저 캐시 때문에 **수정 전 코드를 보고 "통과"라고 보고** | 검증은 **새 origin(포트 변경)**에서. 쿼리스트링은 HTML만 무효화한다 |
| 매일 돈다고 문서에까지 적어 둔 스케줄러가 사흘간 `runs = 0`이었다 | **"등록했다"를 "돌고 있다"로 세지 마라.** 실행 횟수와 마지막 산출물 시각을 봐라 |

### 그래서 지금 쓰는 골격

```xml
<role>
너는 이 도메인의 숫자가 틀리면 사용자가 큰 의사결정을 잘못한다는 걸 아는 시니어 엔지니어다.
</role>

<context>
{{프로젝트 경로}}는 이미 {{N}}개 기능이 돌아가고 있다.
새로 짓는 게 아니라 기존 구조에 얹는다.
</context>

<task>
{{추가·수정할 기능 한 문장. "제안"이 아니라 "구현·검증까지"}}
</task>

<requirements>
1. 계산 로직은 순수함수 모듈, 그리는 코드는 패널 파일로 분리한다.
2. 썩는 값(세율·금리·한도)은 상수 파일에 source·asOf와 함께. 이미 있는 상수를 재구현하지 마라.
3. 새 계산은 손계산 대조 테스트를 같이 쓴다(의존성 0).
4. 외부에서 온 문자열은 이스케이프, 링크는 스킴 화이트리스트를 통과시킨다.
5. 끝나면 문법검사 + 테스트 전량 + 콘솔 에러 0을 증거로 보고한다.
</requirements>

<constraints>
- 데이터가 없으면 지어내지 말고 해당 카드를 숨긴다.
- 판정 불가를 "정상"으로 처리하지 않는다.
- 확정 전 제도(국회 통과 전 개정안)는 계산에 넣지 않고 "예정"으로만 표기한다.
- 기존 출력이 바뀌면 회귀다. 바꿔야 하면 이유를 먼저 말한다.
</constraints>

<success_criteria>
1. {{기능이 되면 성공인 조건 — 검증 가능한 문장으로}}
2. 기존 테스트 전량 + 신규 테스트 pass
3. 콘솔 에러 0, 신규 요소로 인한 레이아웃 깨짐 0
4. 화면의 모든 숫자에 출처와 기준일이 붙는다
</success_criteria>

끝내기 전에 success_criteria를 항목별로 자기검증해 증거와 함께 보고하고,
안 맞으면 고친 뒤 다시 검증한다.
```

> **두 번째 교훈:** 프롬프트는 한 번 쓰고 버리는 게 아니라 **프로젝트와 함께 자란다.**
> 사고가 날 때마다 그 사고를 `constraints` 한 줄로 승격시키면,
> 프롬프트가 그 프로젝트의 **회귀 방지 장치**가 된다. 테스트가 코드에 대해 하는 일을,
> 프롬프트는 다음 세션의 나(또는 에이전트)에 대해 한다.
